# 软件可靠性

教材把可靠性单独列为第 9 章“软件可靠性基础知识”。这部分不要只记一个定义，可以沿着一条工程主线理解：<strong>定义可靠性 → 设定指标 → 建立模型 → 生命周期管理 → 可靠性设计 → 测试与评价</strong>。

## 1. 基本概念

软件可靠性是软件产品在<strong>规定条件</strong>和<strong>规定时间区间</strong>内完成<strong>规定功能</strong>的能力。三个限定词缺一不可：

| 关键词 | 判断重点 |
| --- | --- |
| 规定条件 | 软件运行的计算机系统状态、输入条件和运行环境 |
| 规定时间 | 实际运行时间、自然时间或题目指定的时间基准 |
| 规定功能 | 软件为提供给定服务必须完成的功能 |

可靠性描述的是“能否持续无故障完成规定功能”，要和相近概念区分：

- <strong>可靠性</strong>：规定时间和条件下完成规定功能的能力。
- <strong>可用性</strong>：系统处于可运行状态、能够提供服务的时间比例，和修复时间有关。
- <strong>可维护性</strong>：发现问题、定位问题、修改和恢复的难易程度。
- <strong>容错性</strong>：部分构件发生故障时，系统仍能维持规定服务的能力。

软件和硬件的可靠性问题也不完全相同。软件没有硬件那样的物理退化，失效更多与设计缺陷、输入和运行环境有关；软件版本更新较快，也会增加可靠性评估的难度。

## 2. 可靠性指标与失效率

### 常用指标

| 指标 | 含义 | 题目中的常见线索 |
| --- | --- | --- |
| 可靠度 R(t) | 规定时间内无故障完成规定功能的概率 | “无故障的概率” |
| MTTF | 平均失效前时间，通常指从开始运行到首次失效的平均时间 | 不可修复系统、首次失效 |
| MTTR | 平均恢复前时间，从发生故障到修复成功的平均时间 | 修复、恢复、重新投入使用 |
| MTBF | 平均故障间隔时间 | 两次相邻失效之间的间隔 |

在指数分布、修复时间很短的题设下，常用：

```text
MTBF = MTTF + MTTR
MTBF ≈ MTTF（当 MTTR 很短）
```

失效率或失效强度描述单位时间内发生失效的频度。题目给出单位时间失效率和运行时间时，期望失效次数通常按“失效率 × 运行时间”估算。例如：

```text
10⁻⁶/小时 × 1000 小时 = 10⁻³
```

注意区分<strong>单位时间的失效率</strong>和<strong>一段时间内的期望失效次数</strong>，不要只对指数做加减。

## 3. 软件可靠性建模

软件可靠性模型是为了<strong>预计或估算软件可靠性</strong>而建立的可靠性框图和数学模型，用于把复杂系统的可靠性分解、分配、估算和评价。

一个模型通常包含四部分：

1. <strong>模型假设</strong>：把实际情况进行简化，例如测试用例能够代表实际运行剖面。
2. <strong>性能度量</strong>：模型输出的可靠性指标，例如失效强度、累计失效数或残留缺陷数。
3. <strong>参数估计方法</strong>：当指标不能直接获得时，用数据估计模型参数。
4. <strong>数据要求</strong>：模型运行所需的失效时间、失效次数和运行剖面等数据。

教材强调三类常见假设：

- <strong>代表性假设</strong>：测试用例能够代表软件实际运行剖面。
- <strong>独立性假设</strong>：不同时间发生的软件失效相互独立。
- <strong>相同性假设</strong>：建模时不区分不同失效的严重等级。

影响软件可靠性的因素主要包括运行剖面、软件规模、内部结构、开发方法与开发环境，以及可靠性活动投入。模型不是脱离数据的公式，运行环境和测试数据的代表性会直接影响预测结果。

教材列举的模型类别包括种子法、失效率类、曲线拟合、可靠性增长、程序结构分析、输入域分类、执行路径分析、非齐次泊松过程、马尔可夫过程和贝叶斯分析。考试通常更适合先判断模型的输入、假设和输出，再记具体名称。

## 4. 可靠性管理

软件可靠性管理贯穿软件生命周期，核心不是等到测试阶段才补救，而是从需求阶段开始安排目标、指标、活动、数据和文档。

| 阶段 | 主要可靠性活动 |
| --- | --- |
| 需求分析 | 确定可靠性目标、分析影响因素、确定验收标准、制定管理框架和初步计划 |
| 概要设计 | 确定可靠性度量、制定验收方案、开展可靠性设计、收集数据 |
| 详细设计 | 可靠性设计、可靠性预测、调整计划、收集数据 |
| 编码 | 可靠性测试（含于单元测试）、排错、收集数据 |
| 测试 | 可靠性测试、排错、建模、可靠性评价、收集数据 |
| 实施 | 可靠性测试（含于验收测试）、排错、调整模型、评价和文档化 |

容易出错的判断是：<strong>可靠性建模不属于需求分析阶段的主要工作，而是在测试阶段结合测试数据开展</strong>。需求阶段要先确定目标和验收标准，为后续评价建立依据。

## 5. 可靠性设计

教材认为，在软件设计阶段采取可靠性控制，是保障软件可靠性最有效、最经济、最重要的手段。可靠性设计要在功能、性能、用户需求和开发成本等约束下设定合理目标。

### 容错设计

常见容错技术包括：

- <strong>恢复块设计</strong>：由多个功能相同但设计有差异的程序块组成，当前文本失效时切换到备份文本。
- <strong>N 版本程序设计</strong>：多个独立版本对相同输入执行，通过多数表决降低单个版本故障的影响；重点是相异成分规范评审、相异性确认和背对背测试。
- <strong>冗余设计</strong>：使用不同路径、算法或实现方法的备用模块，避免相同缺陷导致备份同时失效。

### 其他设计技术

- <strong>检错设计</strong>：及时发现故障并报警，但通常不能自动消除故障；要考虑检测对象、检测延时、实现方式和处理方式。
- <strong>降低复杂度设计</strong>：简化结构、缩短代码、优化数据流，把复杂度控制在合理范围内。
- <strong>系统配置技术</strong>：通过双机热备、服务器集群等系统级方案提升容错和持续服务能力。

看到“关闭运行中的一台机器，观察系统能否继续服务”，优先判断为对<strong>容错性</strong>或故障转移能力的测试，而不是可修改性、可移植性或可理解性。

## 6. 可靠性测试与评价

### 广义测试与狭义测试

| 类型 | 核心理解 |
| --- | --- |
| 广义可靠性测试 | 为最终评价可靠性，综合使用建模、统计、试验、分析和评价等手段的完整过程 |
| 狭义可靠性测试 | 在预期使用环境和给定运行剖面下，按测试用例执行测试并获取可靠性数据 |

广义过程通常包括：<strong>确定可靠性目标 → 定义运行剖面 → 设计测试用例 → 实施测试 → 收集和分析数据 → 建模或选择模型 → 可靠性评价</strong>。狭义测试更强调模拟用户实际使用方式并获得可用于评价的数据。

可靠性测试的目的不只是“找缺陷”，还包括：

- 为软件使用和维护提供可靠性数据；
- 分析失效的分布、原因和后果；
- 确认软件是否达到定量可靠性要求；
- 为排错、模型调整和后续可靠性活动提供依据。

可靠性评价要结合模型、运行剖面和可靠性数据，不能脱离测试条件直接比较一个抽象的“可靠程度”。

## 复习抓手

1. 定义题抓住“规定条件、规定时间、规定功能”。
2. 指标题先区分 R(t)、MTTF、MTTR、MTBF 和失效率的口径。
3. 阶段题记住：需求阶段定目标和验收标准，测试阶段建模和评价。
4. 设计题区分恢复块、N 版本、冗余、检错和降低复杂度。
5. 测试题先判断是广义过程还是狭义可靠性试验，再看运行剖面和数据用途。
