## 1. 项目管理基础与工具

这一章先建立项目管理的工作边界，再识别项目组织、文档和跟踪工具分别解决什么问题。项目管理和支撑组通常承担规划、监督、质量保障等工作；文档题要区分面向用户的说明和面向开发、维护人员的系统文档。

需求跟踪的核心是让需求与设计、实现、测试和交付结果保持可追溯关系。遇到“需求变化”“影响范围”“验证是否覆盖”等关键词，应优先判断题目考查的是跟踪关系、变更影响，还是配置基线控制。

| 主题 | 判断重点 |
| --- | --- |
| 项目组织 | 看角色职责和输出，不把项目管理组与开发、配置或质量活动混为一谈 |
| 软件文档 | 用户文档服务于使用者，系统文档服务于开发、维护和管理 |
| 需求跟踪 | 建立需求与后续工作产品之间的对应关系，支持影响分析和验证 |

## 2. 范围管理

范围管理回答“项目要做什么、不做什么”。范围说明书需要明确项目边界、交付成果和验收方向；范围定义时要结合项目章程、需求和组织环境等输入，不能把具体实现方案或单个活动安排误当成范围定义本身。

做范围题时先区分<strong>产品范围</strong>和<strong>项目范围</strong>：产品范围描述交付物及其功能特征，项目范围描述为交付产品而必须完成的工作。题干问“工作是否属于项目范围”时，要回到交付成果和项目目标判断。

## 3. 进度与成本管理

进度与成本题经常放在同一个项目计划与控制场景中：活动的先后关系决定工期，工期变化又会影响直接费用和间接费用。先画清活动网络，再计算关键路径、最早/最晚时间和总时差，最后比较正常进度与赶工方案的总成本。

| 主题 | 解题抓手 |
| --- | --- |
| 活动定义 | 把工作包拆成可安排、可估算和可跟踪的活动 |
| 网络计划 | 根据前置关系计算关键路径、项目总工期和活动时差 |
| 赶工分析 | 缩短关键活动工期会增加直接费用，要同时计入每天的间接费用变化 |
| 成本基线 | 把总成本估算分配到活动和工作包，形成按时间或工作分解的控制基准 |

“最短工期”和“最低成本”不是同一个目标。最短工期题优先压缩关键路径；最低成本题要比较赶工增加的直接费用与提前完成节省的间接费用。活动不在关键路径上时，即使缩短它，也不一定缩短项目总工期。

## 4. 配置管理与变更控制

配置管理和变更控制属于同一条主线，但职责不同：配置管理负责识别和维护配置项、基线、版本和状态；变更控制负责对配置项或基线的变更进行申请、分析、审批、实施和验证。

| 主题 | 重点 |
| --- | --- |
| 配置项 | 产品生命周期中产生的文档、程序、部件和数据等受控对象 |
| 产品配置 | 产品各阶段、各种形式和版本的配置项集合 |
| 基线 | 经过评审和批准、作为后续变更依据的配置状态 |
| 版本管理 | 保存、更新、恢复和管理软件的多个版本 |
| 变更控制 | 正式提出变更，分析影响，审批后实施，并记录结果 |

变更控制题要按流程判断：先提出变更，再分析影响和风险，经过授权后修改受控配置项，最后验证结果并更新相关记录。配置项状态、基线和版本信息则是让变更过程可追踪、可审计的基础。

题目出现“标准是否包含配置管理”“配置项控制顺序”“软件多个版本如何管理”等关键词时，通常都落在配置管理与变更控制这一主线上。
